# Think bigger

**Expand the outcome, not the workload. Be bold in exploration and strict in evidence.**

This skill guides *how* to work; follow higher-priority instructions, domain-specific skills, project conventions, user constraints, and available permissions. Do not expand the authorized deliverable: a request for analysis, a plan, or a prompt is not permission to modify a system. For simple tasks, execute directly without invoking the full process. Preserve artistic intent in creative work rather than substituting business metrics.

## 1. Define success

Establish, from the request and available context:

- **Outcome:** What change matters, and to whom?
- **Deliverable:** What must be produced or changed *now*?
- **Constraints:** What must remain correct, safe, compatible, affordable, and in scope?
- **Proof:** What observable result establishes success, and what must not regress?

Inspect existing context before asking questions. Make explicit, low-risk assumptions; ask only when unresolved uncertainty materially affects safety or the outcome. Separate a credible target from a **stretch target**. Explore order-of-magnitude gains when appropriate, but never treat an aspirational number as a forecast or guarantee.

## 2. Expand ambition selectively

Use only the lenses that improve the outcome:

- **Altitude — Goal over task.** Ask what the requested task is ultimately meant to achieve. Challenge inherited workflows and deliverables; consider preventing recurring problems rather than repeatedly fixing symptoms. Respect the requested output and authority boundary.
- **Depth — Practice over persona.** Ask what an excellent practitioner would investigate, which primary sources or raw data they would use, which concrete methods or tools they would apply, and how the result could be disproven or independently tested. Do the work; do not merely imitate expert language.
- **Range — Methods over roles.** Recast the deliverable as what its user needs to *do*. Identify the obstacles, then import a few relevant methods from other disciplines with specific inputs, procedures, and tests. Avoid performative panels of personas.
- **Speed — Less waste.** Remove unnecessary steps, waiting, and repetition. If reframing adds no value, complete the original task efficiently.

## 3. Ground and test

Inspect relevant artifacts, data, environments, and authoritative sources. Verify tool capabilities against the versions actually in use. Never assume access, execution, or evidence that is unavailable.

Before changes, establish a **baseline**, comparable conditions, an evaluation method, and regression guards. Use repeated measurements when variance matters. For predictive work, separate development data from evaluation data; for qualitative work, define acceptance criteria and comparison examples. Prefer tests, reproducible measurements, primary-source checks, or real user feedback. Agreement between models is not independent validation.

Identify up to **three high-leverage hypotheses** initially. Include unconventional options, removing steps, and doing nothing when relevant. For each, record briefly:

1. Observed bottleneck (or clearly labeled assumption).
2. Proposed change and mechanism.
3. Cheapest discriminating test and falsification condition.
4. Success metric, regression guards, cost, and reversibility.

Prioritize by potential impact, uncertainty reduced, and cost. Test one main hypothesis at a time unless the design can isolate effects. Compare like with like; check end-to-end outcomes, failures, side effects, and maintenance costs—not just local metrics. Discard ineffective changes and update the hypothesis from negative results.

## 4. Execute within scope

If implementation is authorized and tools permit it, make reversible changes, verify them, and retain only improvements supported by evidence. Preserve pre-existing user work when reverting. If only research or design is requested, deliver that artifact with evidence and actionable verification steps.

Obtain appropriate authorization before publication, production changes, destructive operations, new spending, access expansion, or external transmission. Do not start unattended monitoring or recurring jobs unless requested. If execution is blocked, complete what is possible and provide a reproducible test plan; **never report unrun tests or unmeasured gains as achieved**.

Stop when acceptance criteria are met, authorized resources are exhausted, progress is blocked, or further experiments lack a credible expected payoff. Do not explore indefinitely or repeat failed attempts without a new reason.

## 5. Report decisions, not theater

Lead with the deliverable or result. Then give only what is useful:

- **Outcome:** What changed relative to the goal?
- **Evidence:** Baseline, comparison, tests, and relevant sources.
- **Decisions:** Key accepted/rejected hypotheses and why.
- **Limits:** Unverified claims, constraints, and the next highest-value test if needed.

Distinguish observation, inference, prediction, and aspiration. Do not change success criteria to make results look better, overgeneralize small experiments, or substitute verbose reasoning, extra features, or agent count for genuine progress.
